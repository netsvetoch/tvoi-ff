## Context

Профиль (`src/pages/profile/ProfilePage.tsx`) уже запрашивает достижения пользователя (`getAllAchievementsUserUserIdGetOptions`), но показывает только достижения с картинками, используя относительный `picture` как `src` (работает только на origin, раздающем статику achievement-сервиса). achievement-клиент (`src/shared/api/achievement/`) полностью сгенерирован и не используется остальными эндпоинтами. Базовый URL клиента — `https://api.test.profcomff.com/achievement`; картинки отдаются по `{baseUrl}/static/{id}.png`. См. proposal.md — Why.

Ограничения, проверенные на тестовом API:

- У текущего тестового аккаунта нет скоупов `achievements.achievement.*`: мутации возвращают 401 «Not authorized» (без токена) или «Не хватает прав» (при попытке запросить скоупы во входах) — права проверяет сервер.
- Запрос скоупов при входе, которых у пользователя нет, завершает вход ошибкой 403, поэтому менять вход нельзя.
- `GET /achievement`, `GET /user/{user_id}`, `GET /achievement/{id}/reciever` доступны с токеном сессии.

## Goals / Non-Goals

**Goals:**

- Закрыть все эндпоинты `src/shared/api/achievement/` интерфейсом на странице `/profile`.
- Починить отображение собственных достижений (абсолютные URL картинок, достижения без картинок, название и описание).
- Единый с остальным приложением паттерн: сгенерированные TanStack-хуки, `useLoginData().token` в `auth`, тосты об успехе/ошибке, диалоги подтверждения.

**Non-Goals:**

- Не менять сгенерированный клиент (`src/shared/api/achievement/`) и не менять флоу входа/скоупы.
- Не вводить отдельных маршрутов и пунктов навигации: всё живёт на `/profile`.
- Не строить права на клиенте (не прятать кнопки по скоупам): скоупы в сессии не запрашиваются, а сервер всегда проверяет права сам.
- Не реализовывать поиск/пагинацию/фильтры каталога — список достижений короткий.
- Не вызывать `GET /achievement/{id}` напрямую: он возвращает тот же объект `AchievementGet`, что и элемент ответа `GET /achievement`, поэтому отдельный сценарий «достижение по id» в интерфейсе профиля отсутствует — данные каждого достижения уже есть в каталоге.

## Decisions

### Размещение: секция в основном контенте профиля + исправленная карточка в aside

Каталог с действиями (создание/редактирование/удаление/картинка/получатели) не помещается в узкую aside-колонку, поэтому:

- aside-карточка «Достижения» остаётся витриной собственных достижений пользователя (исправленная);
- в основной контент под карточками пользовательских данных добавляется секция «Достижения» (заголовок `header-2`) с каталогом и действиями.

Альтернатива (отдельная страница `/achievements`) отвергнута: требование — «в профиле», а новая навигация раздута бы объём изменения.

### Карточка достижения в каталоге

`Card` с картинкой (или заглушкой `Avatar`/плейсхолдер), названием, описанием, владельцем (`Пользователь №{owner_user_id}`) и меню действий (`Popup`/кнопки): «Изменить», «Картинка», «Получатели», «Удалить». Список — `Flex direction="column"` (как карточки броней в прокате), без таблицы: записей немного, у каждой богатый набор действий.

### Диалоги

Один переиспользуемый диалог формы достижения (`Диалог достижения`) на создание и редактирование: `TextInput` «Название» + `TextArea` «Описание», валидация непустого названия на клиенте. Отдельные диалоги: подтверждение удаления (`Dialog.Footer preset="danger"`, паттерн отмены брони в прокате), загрузка картинки (`FileDropZone` из `@gravity-ui/uikit/unstable` + `FilePreview`, валидация `image/*` и непустого файла — паттерн `LecturerPhotos`), получатели (список `Пользователь №{user_id}` с действием «Отозвать» + поле ввода `user_id` и кнопка «Выдать»).

### Ключи запросов и инвалидация

- Каталог: `getAllAchievementsAchievementGetOptions({ auth: token })`.
- Собственные достижения: существующий запрос не меняется.
- Получатели: `getAllRecieversAchievementAchievementIdRecieverGetOptions` лениво (диалог открывается по действию), `enabled` по открытому достижению.
- После любой мутации инвалидируются ключи каталога (`getAllAchievementsAchievementGetQueryKey()`) и собственных достижений пользователя (`getAllAchievementsUserUserIdGetQueryKey(...)`); после выдачи/отзыва — также ключ получателей конкретного достижения. Иначе `stale` данные остаются в кэше.

### Разрешение URL картинок

В `src/shared/helpers` добавляется `resolveServiceAssetUrl(link, baseUrl)` — обобщение существующего `resolveTimetablePhotoUrl` (абсолютные http(s) сохраняются, относительные разрешаются против базового URL, небезопасные схемы отбрасываются), чтобы не дублировать логику; `resolveTimetablePhotoUrl` переопределяется через него без изменения поведения (покрыт тестами). Базовый URL берётся из `client.getConfig().baseUrl` achievement-клиента (паттерн `LecturerPhotos`).

### Сообщения об ошибках

Локальный в модуле профиля хелпер разбора ошибок по образцу `getRentalErrorMessage` (`ru` → `detail` строка/массив → «Неизвестная ошибка») — без выноса в `shared`, чтобы не трогать прокат; дублирование осознанное и маленькое.

## Risks / Trade-offs

- [Пользователи без прав видят действия и получают ошибки сервера] → Так задумано (см. Non-Goals): тост с текстом сервера объясняет причину; поведение зафиксировано в спеке.
- [Тестовый API нестабилен: отдельные запросы таймятся] → Запросы через TanStack Query с состояниями загрузки/ошибки; ошибка получения каталога показывается текстом.
- [`uploadPicture` требует `FormData` с полем `picture_file`] → Сгенерированный клиент уже подключает `formDataBodySerializer`; передаётся `body: { picture_file: file }`.
- [`recievers` содержит только `user_id`, без имён] → Показываем «Пользователь №{user_id}»; резолв имён недоступен в achievement API и не запрашивается.
